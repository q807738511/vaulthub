# VaultHub 弱网使用方案（面向远程访问与移动网络）

> 适用版本：v0.9.71 起（v0.9.67 起已有漫画省流与页转码；本版补齐音频限码率与自动测速）
> 目标读者：把 VaultHub 装在自己 NAS 上、需要从公司/4G/亲友网络访问的部署者。

## 1. 为什么需要这套方案

Plex、Emby、Navidrome 在「带宽不足」这条赛道上都收敛到同一套结论，VaultHub 沿用同样的思路：

| 项目 | 主要做法 | 对 VaultHub 的启发 |
| --- | --- | --- |
| Plex | 客户端「自动质量」+ 服务端按带宽选择转码档位（含 HLS 自适应） | 需要一个**客户端可感知带宽**的入口，服务端要有码率档位 |
| Emby | 同上，另有「限速播放」与影院模式码率上限 | 档位要显式可选，且能一键降级 |
| Navidrome | 客户端选码率 → 服务端 ffmpeg 转 opus/mp3 → 结果缓存复用 | 音频转码落地与缓存复用是最划算的一项 |

浏览器 `<audio>` 没有 HLS/DASH 那样的自适应能力，因此 VaultHub 采用 Navidrome 式的
「客户端选档位 + 服务端转码 + 结果落盘复用」，并加上一条轻量测速来自动选档。

## 2. 容器侧已有的能力（无需配置）

| 能力 | 说明 | 验证方式 |
| --- | --- | --- |
| 静态资源压缩 | 容器内 Caddy 已开启 `encode zstd gzip`（首屏 JS/CSS 体积下降约 70%） | `curl -H 'Accept-Encoding: gzip' -sI https://<你的域名>/web/js/02-media.js` 应看到 `Content-Encoding: gzip` |
| 媒体流 Range | `/api/media/file` 用 `http.ServeContent`，支持 `Accept-Ranges: bytes`（视频/音频可拖动、可断点续传） | `curl -r 0-99 -sI` 应返回 `206` |
| 封面私有缓存 | 封面/转码页带 `Cache-Control: private` + ETag，二次进入不重复下载 | 浏览器 DevTools 看 Size 列出现 `(disk cache)` |
| 漫画页转码 | 阅读器「省流」档：单页转 JPEG（约原图 39%–56%），内容寻址磁盘缓存 | 打开 CBZ，工具栏「省流·自动」→ 切「省流·开」 |

## 3. v0.9.71 新增：音频限码率与自动测速

### 3.1 服务端接口

```bash
# 限码率音频流（转码结果缓存在 <MEDIA_CACHE_DIR>/audio-transcode/<sha1>.mp3，默认 7 天）
curl -b cookies.txt -o /tmp/song-128k.mp3 \
  'http://<host>:8088/api/media/audio/stream?id=<库ID>&path=<相对路径>&bitrate=128k'
# 缓存命中时响应头：X-Vaulthub-Audio-Cache: hit；首次为 miss
# 允许档位：64 / 96 / 128 / 160 / 192 / 256 / 320（kbps）
# 转码队列拥塞（与视频/漫画转码共用全局闸门）会返回 503 + Retry-After: 3，前端自动回落原文件

# 客户端下行测速（返回不可压缩随机数据，禁用压缩与缓存）
curl -b cookies.txt -o /dev/null -w '%{speed_download} B/s\n' \
  'http://<host>:8088/api/media/weak/probe?kb=512'
```

### 3.2 客户端行为

- **弱网模式**（系统设置 → 弱网模式）：
  - `自动`（默认）：后台测速，`< 400 KiB/s` 判定弱网 → 音频走 96k 转码、漫画省流自动开启；
    `400 KiB/s – 1.5 MiB/s` 判定中等 → 音频 160k；更高则原文件直出。
  - `始终开启`：不管测速结果都用 96k + 省流（适合长期用移动网络）。
  - `关闭`：一律原文件/原图直出（适合纯内网）。
- **音质药丸**（播放器上的「音质·原文件」按钮）：点按循环
  `原文件 → 自动 → 320k → 192k → 128k → 96k`，显式选择优先于自动判定，切换时保持播放位置。
- **回落策略**：转码流失败（503、ffmpeg 异常、网络中断）自动回落到原文件直出，不会卡死播放。
- **测速结果 30 分钟内复用**，不会每次进入都打探测接口。

### 3.3 相关环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `MEDIA_CACHE_DIR` | `/data/transcode-cache` | 转码缓存根目录（视频/漫画页/音频共用） |
| `MEDIA_CACHE_MAX_BYTES` | `10 GiB` | 主缓存上限；音频转码缓存上限取 `min(2 GiB, 该值/2)` 并按「最旧先删、1 小时内不动」清理 |
| `VAULTHUB_LYRICS_NETEASE` | `0` | 歌词源开关（与弱网无关，此处仅作提示：默认关闭） |

音频转码缓存是**独立配额**，不会把漫画页缓存挤掉。

## 4. 面向不同客户场景的推荐配置

### 4.1 纯内网 / 同一交换机（最常见）

- 弱网模式保持 `自动`；`MEDIA_CACHE_MAX_BYTES` 给 10–20 GiB 即可。
- 不需要为音频开转码：LAN 下原文件（FLAC/320k）直出更快、更省 CPU。
- 建议在反代开启 HTTP/2 或 HTTP/3，多封面并发更顺。

### 4.2 远程访问（公司网络 / 4G / 亲友家）

1. **接入侧**：Cloudflare Tunnel 或 frp/FRPS 都可用，但请把**大文件走直连域名的同源路径**
   （`/api/media/*`）而不是套一层会缓冲整响应的反代；VaultHub 的转码流是分块输出，
   中途被反代全量缓冲会显著增加首字节时间。
2. **容器侧**：`MEDIA_CACHE_DIR` 指到 SSD 卷（例如 `/vol3/1000/监控/date`），
   转码缓存命中后重播几乎零成本。
3. **客户端侧**：弱网模式 `自动`；如果用户长期在移动网络，建议直接教他们切到 `始终开启`。
4. **CPU**：单个 128k MP3 转码约 0.2–0.5 核，NAS 上通常不是瓶颈；
   50 人以上并发时才需要限制（全局转码闸门默认 `min(3, max(2, CPU/2))`）。

### 4.3 移动端为主（手机浏览器/PWA）

- 视频先选 `720p` 或 `480p`（播放器右上角质量菜单），音频让它走 96k。
- 漫画建议固定「省流·开」+「条漫」模式，预取窗口默认前后 3 页。
- 如果手机常在地铁/电梯，弱网模式设 `始终开启`，避免每次都要等测速。

## 5. 常见问题

**Q：为什么音频转码后时长/进度条不对？**
A：转码流是重新编码的 MP3，时长由解码器重建，正常情况下与源一致；
若源文件本身损坏（ffmpeg 报错），服务端返回 500，前端会回落原文件。

**Q：能不能指定 opus 更省流量？**
A：暂时只提供 MP3（浏览器全平台可播，含 Safari）；opus 需要 OGG 容器，
部分 Safari 版本支持不佳，会在后续版本评估按客户端能力选择编码。

**Q：转码会不会吃掉 NAS 的 CPU？**
A：全局转码闸门与视频/漫画转码共用，队列拥塞时返回 503 让客户端回落原文件，
不会把 CPU 打满到影响其它服务。

**Q：为什么测速显示「良好」但播放仍卡？**
A：测速只测本机到服务的下行；如果卡的是**上行**（例如异地 NAS 家宽上行只有 20 Mbps），
把弱网模式切到 `始终开启` 强制 96k 更稳妥。
